# 怎么一起把Pre做得更好

先读[主线地图](项目主线与内容地图.md)，选择[任务](协作任务板.md)，复制[Codex提示词](Codex协作提示词.md)。仓库已有协作者；领取人仍按实际确认登记。

## 一次合作会怎样走

例如，协作者接T01，发现19页一下引入两个项目，听众不知道该先记住什么。他的Codex交出原句、替换讲法、投影配合和对20页转场的影响。组长逐条决定采纳、调整、暂缓或不采纳，再把接受的内容同步进源稿、备注与下一修订。协作者对照新稿，看原问题是否解决。

这是流程示例，不是已经发生的贡献记录。**提案进入仓库和正式稿采用，是两个状态。**

| 环节 | 协作者负责 | 组长负责 |
|---|---|---|
| 选任务 | 选一个ID，说清页码与范围 | 避免重复，不强绑上台角色 |
| 改进 | 交可替换文字或独立素材 | 保持全场主线，回答范围问题 |
| 审阅 | 给理由、依据与牵动文件 | 逐条作决定，不只回复“收到” |
| 整合 | 默认不覆盖交付PPT | 同步源稿、引用、备注与导出 |
| 复核 | 看采用后的页面与讲法 | 保存检查，更新当前版本 |

当前主代理负责协作文档；T01—T05尚未登记领取人。选任务前看打开的Issues/PR，或本人在小组现有沟通渠道说一句“我接T01的14—23页”。Agent不自动代发群消息；不为领取任务另建一套复杂表。

## 在自己的Codex里开始

用GitHub Desktop克隆，或让Codex运行：

```text
git clone https://github.com/Cyh29hao/ai-agent-rnd-course-project.git
```

仓库是private，使用协作者自己的GitHub权限。已有副本时先看`git status`和当前分支，再`git fetch origin main`。只有当前在main、工作区干净且允许快进时才`git pull --ff-only origin main`。在自己的协作分支时保留该分支，比较它与`origin/main`的差异，由Codex说明怎样更新，不把拉取分支上游当成更新main。有改动或分叉先保留，不reset。然后粘贴启动提示与任务。

无需原聊天，也不要共享组长账号、令牌或完整私有对话。

## 提案与素材放哪里

默认文字放`collaboration/proposals/<自己的英文短名>/<任务ID>-<主题>.md`，素材放`collaboration/assets/<短名>/<任务ID>/`。例如`collaboration/proposals/chen/T01-14-23-oral.md`；示例短名不是分工。

按[提案模板](修改提案模板.md)写。优先交最值得改的几处，逐项给原文、新文、定位、理由、投影配合和牵动文件。查事实时给文献号、节/图/页和链接；查不到就标未查。

如果任务明确允许直接改源稿，可以在自己的分支修改约定文件；相关源稿需同步，没导出时明说正式PPT仍是05。普通提案不改当前版本清单。

## 怎么提交

让Codex建`collab/<短名>/<任务ID>-<主题>`分支，只提交本任务文件，push该分支并准备PR。不混入他人改动、不强推main、不自动合并。提交信息描述为什么改，并记录必要检查：

```text
Help listeners follow the transition to agent self-modification

Constraint: Preserve the presentation scope and deferred practice
Tested: Compared proposed wording with slides 19 and 20; documentation checks passed
Not-tested: Human timing and regenerated PowerPoint
```

不能联网时交回提案文件与素材，组长可代交并标实际建议来源。不把本地保存说成PR已提交。

组长在提案顶部填写整合状态，并逐条写决定、理由、对应正式修订与检查。未采用的内容仍是建议，不能被下一位Agent当成当前事实。

## 检查与制作怎么分

普通协作者只需Python 3与Git：

```text
python scripts/check_collaboration_docs.py
git diff --check
```

这确认入口、链接、UTF-8和交付文件散列，不评价论证质量。学术结论仍要看原文；真人理解和计时仍要实际进行。

PPT制作依赖Codex的`@oai/artifact-tool`和组长本机路径，原生导出需要Windows Office；目前不是任意电脑克隆即能构建。默认不要求协作者安装新依赖或跑整个制作过程。旧`verify_closing.py`会写文件并固定检查04→05，不作通用只读检查。具体联动看[文件地图](项目主线与内容地图.md#文件地图与修改联动)。
