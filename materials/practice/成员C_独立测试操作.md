# 成员 C：真正独立最终测试的操作

这是将来四人亲自操作的指南；共同工作区内的 `demo/` 不是这批测试。

1. 在**自己的设备和私有目录**制作16条新题，四标签各4条；从 S1–S4 的官方原文选择事实族，避开 `dev/` 的同一事实、数字及近义改写。可看开发题排重，A、B、D和制作代理在候选冻结前不能看新题与答案。每条记录原文 URL、节/图、可回读 fragment ID、中文摘要、标签和裁定理由。保留真实核查日期。
2. 输入文件仅包含 `claim_id/claim/source_ids`；答案文件另存 `claim_id -> label`，记录二者 SHA-256 与制作时间。不要把答案文件放进给 Agent 的目录或运行消息。给 A 一份**匿名、无标签**事实定位供其预核来源；如需要两人确认标签，在冻结后且运行前由 A 核，并记录分歧及最终裁定，A 不再调候选。
3. 在看到新题前由 D 冻结基线、候选提示和执行配置，保存 SHA-256。每题独立会话，按预先确定顺序让 B 跑两种提示，模型、工具、来源、上限相同，输出原始 JSON 和公共动作日志；采样若不可控如实记载。执行者不能在优化上下文提前接触题目。
4. 两轮都结束后由 C 用固定 `score.py` 评分，A 对匿名输出人工核证据定位，C 保存分歧处理与逐题配对。若有泄漏、执行失败或提示修改，不删试次，报告实际过程和限制。结果绝不回流改本批候选；再改须另开新测试批次。

若 C 无法在另一设备保管，或题目在冻结前已进入同一个全权限 Codex，写明“无独立最终测试”，只展示 `demo/` 流程，不能写“盲测”“sealed holdout”“泛化提升”。
